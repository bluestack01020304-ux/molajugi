# 몰아주기 설계 문서

작성일: 2026-11-07
상태: 승인됨 · 구현 완료 (2026-11-07). 구현 계획: `docs/superpowers/plans/2026-11-07-molajugi.md`

## 1. 한 줄 요약

판매자가 안 쓰는 기프티콘을 올리면, 구매자가 액면가보다 싼 값을 내고 정해진 확률로 뽑는 앱.
당첨이면 구매자가 기프티콘을 받고, 꽝이면 판매자가 돈을 받는다. 플랫폼은 매 뽑기마다 수수료를 뗀다.

## 2. 왜 만드는가

사용자가 직접 겪은 두 장면에서 출발했다.

- **사는 쪽.** 돈이 애매하게 남았는데 먹고 싶은 게 있을 때, 정가는 부담스럽고 "잃어도 좋으니 반값 걸고 운에 맡겨보고 싶다"는 마음. 이 앱의 핵심은 할인이 아니라 그 **긴장감**이다.
- **파는 쪽.** 선물받은 기프티콘을 쓸 일이 없고, 중고 앱에 올리자니 번거롭고 수수료도 크고, 묵히다 만료되는 애매함. 올려두면 누군가 걸어보고, 꽝이면 돈이 들어오는 가벼운 처분 수단.

이 두 장면을 모두 살리는 게 목표다. 할인 거래만 남기면 첫 번째 장면이 사라져서 기존 기프티콘 거래 앱의 열화판이 된다.

## 3. 이 단계의 목표와 비목표

### 목표

- 판매자 등록 → 구매자 뽑기 → 당첨/꽝 → 정산까지 **전체 흐름이 실제로 동작하는 앱**을 만든다.
- 실제 폰(아이폰, 안드로이드)에서 Expo Go로 돌려보고, 지인에게 보여줄 수 있는 수준.
- 뽑기 확률, 가격 보기, 수수료율, 정산 보류 기간 같은 **규칙은 한 곳에 모아** 나중에 통째로 갈아끼울 수 있게 한다.

### 비목표 (이번 단계에서 하지 않음)

- 실제 결제(PG) 연동. 포인트 지갑으로 흉내 낸다.
- 포인트 출금(현금화). 버튼은 "준비중"으로만 둔다.
- 바코드 이미지에서 브랜드/액면가/유효기간 자동 인식(OCR). 판매자가 손으로 입력한다.
- 발행사(카카오 등)와의 연동이나 기프티콘 사용 여부 자동 검증.
- 운영자 전용 화면. 분쟁 처리는 Supabase 대시보드에서 데이터를 직접 고치는 수준.
- 앱스토어 배포.
- 카카오/구글 소셜 로그인.

### 안티골 (이렇게 되면 실패)

- 뽑기 결과를 앱(클라이언트)에서 정하는 구조. 조작 가능하면 전부 무의미하다.
- 규칙이 화면 코드 여기저기에 흩어져서 법률 상담 뒤 바꾸려면 앱 전체를 뒤져야 하는 구조.
- 긁는 연출이 없거나 밋밋해서 "그냥 반값 할인 앱"처럼 느껴지는 것.

## 4. 제약과 전제

### 법적 전제 (중요)

돈을 내고 확률로 재산상 이익·손실이 갈리는 구조는 한국에서 사행행위 규제(사행행위 등 규제 및 처벌 특례법, 형법 복표발매죄·도박개장죄)에 걸릴 가능성이 크다. 랜덤박스와 달리 **"꽝이면 아무것도 못 받는다"**는 점이 결정적 차이다.

사용자의 결정: **일단 만들어보고, 그 뒤 법률 상담 결과에 따라 규칙을 바꾼다.**
그래서 이 문서의 모든 "규칙"은 잠정값이며, 다음 둘은 설계의 필수 요건이다.

1. 실제 돈이 오가지 않는다 (포인트 지갑, 무료 충전).
2. 뽑기·정산 규칙은 서버의 한 모듈과 설정값 한 곳에만 존재한다.

정산을 플랫폼이 보류하는 구조는 나중에 실제 돈이 붙으면 전자금융거래법(결제대금예치업·PG 등록) 문제가 생긴다. 실결제 단계에서는 외부 PG사 에스크로를 쓰는 것으로 자리를 비워둔다.

### 기술적 전제

- 기프티콘 바코드 이미지는 복제 가능하다. 판매자가 등록 후 몰래 쓰는 걸 기술로 막을 수 없다. 대신 **당첨 건의 정산을 보류**해서 쓸 동기를 없앤다(5절 정산).
- 사용자는 TypeScript를 배우며 만든다. 언어는 하나로 통일한다.

## 5. 동작 규칙 (사용자가 정한 것 / 작성자가 정한 것)

"[사용자]"는 대화에서 사용자가 직접 정한 것, "[작성자]"는 작성자가 기본값으로 정한 것이며 사용자가 바꿀 수 있다.

### 등록

- 판매자는 바코드 이미지를 갤러리에서 올리고, 카테고리·브랜드·상품명·액면가·유효기간을 입력한다. [사용자]
- 확률은 **정해진 보기 중 선택**한다. [사용자]
- 보기는 25%, 50%, 75% 세 가지. 가격 = 액면가 × 확률, 10원 단위 반올림. 어느 보기든 판매자 기대 수익은 액면가와 같다. [작성자]
  - 예: 2,000원 → 500원/25%, 1,000원/50%, 1,500원/75%
- 카테고리: 카페, 편의점, 치킨·피자, 베이커리·디저트, 외식, 기타. [작성자]
- 유효기간이 2일 미만 남은 기프티콘은 올릴 수 없다. [작성자]
- 바코드 번호는 **선택 입력**이다. 적으면 당첨 화면에서 이미지 아래에 크게 보여주고, 안 적으면 이미지만 보여준다. 번호는 이미지와 같은 등급의 비밀로 다룬다(당첨 전 비공개, 당첨 후 판매자에게 숨김). [작성자]
- 본인이 올린 기프티콘은 본인이 뽑을 수 없다. [작성자]

### 뽑기

- 구매자는 목록에서 골라 상세를 보고, 포인트를 내고 뽑는다. 결과는 **서버가 결제 즉시 확정**한다. [사용자]
- 꽝이면 기프티콘은 목록에 그대로 남고 다음 사람이 또 뽑을 수 있다. 판매자는 꽝이 날 때마다 돈을 받으므로 액면가보다 많이 벌 수도 있다. [사용자]
- 당첨이면 목록에서 내려가고 구매자에게 바코드가 보인다. [사용자]
- 한 사람이 같은 기프티콘을 여러 번 뽑는 것도 허용한다. [작성자]
- 포인트가 부족하면 뽑기 버튼은 비활성이고 충전으로 안내한다. [작성자]

### 정산

- 당첨이든 꽝이든 구매자가 낸 금액에서 수수료를 뺀 나머지가 판매자 몫이다. [사용자]
- 수수료율 기본 10%. 설정값이다. [작성자]
- 꽝: 판매자 포인트 지갑에 즉시 적립. [작성자]
- 당첨: 그 한 건만 **보류**. 구매자가 "정상 사용했어요"를 누르면 적립. 아무 응답 없이 **3일**이 지나면 자동 적립. 구매자가 "이미 쓰인 바코드예요"를 누르면 보류 상태로 멈추고 "분쟁" 상태가 된다. [작성자, 보류 방식은 사용자 선택]
- 분쟁 해결은 운영자가 데이터베이스에서 직접 한다. 결과는 둘 중 하나: 판매자에게 적립, 또는 구매자에게 환불(낸 포인트 전액). [작성자]

### 만료와 알림

- 유효기간 **7일 전과 1일 전**에 판매자에게 알림. 매일 한 번 서버 작업이 검사한다. [사용자 요청, 일수는 작성자]
- 알림의 기본 경로는 **앱 내 알림함**(내 정보 탭에 목록, 탭 아이콘에 뱃지)이다. 푸시는 그 위에 얹는 덤이며, 동작하는 기기에서만 간다. 이유: Expo Go는 안드로이드에서 원격 푸시를 지원하지 않아서, 푸시를 필수로 두면 "심사 없이 폰에서 바로 실행"이 깨진다. [작성자]
- 유효기간 전날이 되면 자동으로 목록에서 내려간다(당첨자에게 최소 하루는 남기기 위해). [작성자]
- 판매자는 뽑히기 전까지 언제든 내릴 수 있다. [사용자]
- 뽑기가 일어날 때마다(당첨/꽝) 판매자에게 알림. [작성자]

### 지갑

- 모든 사용자는 포인트 지갑 하나를 가진다. 구매자 결제와 판매자 수익 모두 같은 지갑이다. [작성자]
- "충전"은 테스트용으로, 누르면 정해진 포인트가 그냥 들어온다. [사용자: 가짜 지갑]
- "출금"은 준비중 표시만. [작성자]

## 6. 화면 (사용자가 목업을 보고 확정)

하단 탭 4개: **뽑기 · 내 기프티콘 · 판매 · 내 정보**. 오른쪽 위에 포인트 잔액 상시 표시. UI는 한국어.

### 뽑기 (구매자 홈) — 리스트형 [사용자 선택]

- 한 줄에 하나씩. 썸네일, 브랜드, 상품명, 액면가, 남은 기간, 확률 뱃지, 가격.
- 상단 필터는 **카테고리** 칩(전체/카페/편의점/…)이다. 확률 필터는 두지 않는다. [사용자]
- 한 화면에 6개 이상 보이는 밀도.

### 상세

- 상품 이미지(썸네일 크게), 상품명, 액면가, 당첨 확률, 유효기간(남은 일수), **이 기프티콘의 지금까지 꽝 횟수**.
- 하단: "내 포인트 3,500P → 2,500P" 안내와 "1,000P로 뽑기" 버튼.

### 결과 연출 — 긁는 복권 [사용자 선택]

- 결제가 끝나면 회색 코팅 화면이 뜨고, 손가락으로 긁으면 아래에서 "당첨" 또는 "꽝"이 드러난다.
- 결과는 서버에서 이미 정해져 있고, 긁는 건 그 결과를 보여주는 포장이다.
- 당첨이면 다음 화면에서 바코드가 바로 보이고, 꽝이면 "같은 기프티콘 다시 뽑기"와 "목록으로" 버튼이 보인다.
- 충분히 긁지 않아도 일정 시간 뒤 자동으로 다 드러나게 할지는 빌더 판단.

### 내 기프티콘 (당첨 후)

- 바코드 이미지와 번호를 크게. 유효기간.
- 안내문: "매장에서 사용한 뒤 아래 버튼을 눌러 주세요. 3일 안에 응답이 없으면 정상 사용으로 처리됩니다."
- 버튼 둘: **정상 사용했어요** / **이미 쓰인 바코드예요**.
- 목록에서는 상태(사용 확인 대기, 확인됨, 분쟁)를 뱃지로.

### 판매

- **올리기 화면**: 이미지 선택 영역, 카테고리, 브랜드/상품명, 액면가, 유효기간, 확률 보기 3개(고르면 가격 표시), 그 아래 한 줄 설명("꽝이 날 때마다 900원이 들어오고, 당첨되면 기프티콘이 넘어갑니다"), 올리기 버튼. 긴 화면이므로 스크롤 가능해야 하고 버튼이 잘리면 안 된다.
- **내 판매 목록**: 각 줄에 상품명, 확률, 꽝 횟수, 누적 정산액, 상태 뱃지(판매중 / 정산 대기 / 만료 임박 / 당첨 완료 / 내림 / 만료). 판매중인 건 눌러서 내릴 수 있다.

### 내 정보

- 포인트 잔액, 충전(테스트), 출금(준비중), 로그아웃.

## 7. 기술 선택 [작성자, 사용자가 위임]

| 영역 | 선택 | 이유 |
|---|---|---|
| 언어 | TypeScript (앱, 서버 모두) | 배울 언어 하나. 돈과 확률을 다루므로 타입 검사가 사고를 막는다 |
| 앱 | Expo (React Native) | Expo Go로 심사 없이 실제 폰에서 바로 실행. 갤러리 접근, 푸시 알림이 쉽다. 웹에서도 돌아간다 |
| 백엔드 | Supabase | PostgreSQL DB, 인증, 이미지 저장소, 서버 함수가 한 묶음. 무료 구간으로 충분 |
| 인증 | Supabase 이메일+비밀번호 | 가장 단순. 소셜 로그인은 비목표 |
| 알림 | 앱 내 알림함 + Expo Push(덤) | Expo Go 안드로이드는 푸시 불가. 알림함이 기본이라 어느 폰에서든 기능이 보인다 |
| 실행 환경 | Expo Go, 내 폰 중심 | 개발 PC와 같은 Wi-Fi에서 QR로 실행. 지인에게는 내 폰을 건네거나 같은 Wi-Fi에서 보여주는 수준. 별도 빌드·배포는 비목표 |
| 결제 | 없음 (포인트 지갑 테이블) | 실결제는 비목표 |

### 서버 쪽 필수 요건

- **뽑기 처리는 서버에서 하나의 원자적 트랜잭션**으로: 포인트 차감 → 확률 판정 → 뽑기 기록 생성 → (당첨이면 목록 상태 변경 + 보류 정산 생성 / 꽝이면 즉시 정산 + 꽝 횟수 증가) → 결과 반환. 중간에 실패하면 전부 되돌린다. 같은 기프티콘을 두 사람이 동시에 뽑아도 한 번에 하나씩 처리되도록 해당 목록 행을 잠근다. 클라이언트는 "뽑기 요청"만 보낸다.
- **서버 로직은 TypeScript로 쓴다** (Supabase Edge Function 안에서 DB 트랜잭션을 직접 연다). Postgres 함수(PL/pgSQL)로 쓰는 쪽이 더 단순할 수 있지만, "배울 언어 하나"와 "확률 굴리는 곳을 한 파일에서 찾는다"는 목표를 위해 TypeScript를 택한다. SQL은 테이블 정의, RLS 정책, 일일 작업 예약(pg_cron 한 줄)에만 쓴다. [작성자]
- **규칙은 한 곳에**: 확률 보기(25/50/75), 수수료율, 보류 일수, 알림 일수, 최소 잔여 유효기간, 테스트 충전액. DB의 설정 테이블이든 서버 모듈의 상수 파일이든 한 곳이어야 하고, 뽑기·정산 로직도 서버 모듈 하나에 모은다.
- **바코드 이미지는 비공개 버킷**. 서명된 URL로 판매자 본인과 당첨자만 볼 수 있다. 당첨 뒤 판매자 앱에서는 이미지를 숨긴다(원본은 판매자 폰에 있다는 건 전제로 인정).
- **행 수준 보안(RLS)**: 다른 사람의 지갑·뽑기 기록·바코드에 접근 불가.
- **매일 한 번 도는 작업**: 만료 임박 알림(7일/1일 전), 전날 자동 내리기, 3일 지난 보류 정산 자동 적립. TypeScript Edge Function으로 만들고 pg_cron이 매일 호출한다. 기준 시간대는 한국(KST).

### 데이터의 큰 그림 (상세 스키마는 빌더)

- 사용자(프로필, 푸시 토큰), 지갑(잔액), 지갑 거래 내역
- 기프티콘 목록(판매자, 카테고리, 브랜드, 상품명, 액면가, 유효기간, 이미지 경로, 확률, 가격, 상태, 꽝 횟수)
- 뽑기 기록(목록, 구매자, 낸 금액, 결과, 시각)
- 정산(뽑기 기록, 판매자, 금액, 수수료, 상태: 즉시완료/보류/확인완료/자동완료/분쟁/환불)
- 설정(규칙 값)

## 8. 빌더에게 맡기는 것

- 프로젝트 구조, 폴더 배치, 상태 관리 방식, UI 컴포넌트 라이브러리 선택.
- DB 스키마의 정확한 컬럼과 인덱스, RLS 정책 문구.
- 긁기 연출의 구현 방식(Skia, 캔버스 등)과 "자동으로 다 드러나기" 여부.
- 로컬 개발 환경(Supabase 클라우드 무료 프로젝트 vs Supabase CLI 로컬).
- 테스트 데이터(샘플 기프티콘, 테스트 계정) 생성 방법.
- 썸네일: 브랜드별 이미지가 없으므로 카테고리 아이콘이나 브랜드 이니셜로 대체.

## 9. 성공의 모습

- 폰 두 대(또는 계정 두 개)로 한 쪽이 기프티콘을 올리고, 다른 쪽이 뽑아서 긁고, 당첨/꽝에 따라 양쪽 지갑과 목록 상태가 맞게 바뀐다.
- 당첨자가 "정상 사용"을 누르면 판매자 지갑에 돈이 들어오고, "이미 쓰인 바코드"를 누르면 분쟁 상태로 멈춘다.
- 설정값 하나를 바꾸면 수수료율과 보류 기간이 앱 전체에 반영된다.
- 사용자가 코드를 읽으며 "어디서 확률을 굴리는지"를 한 파일에서 찾을 수 있다.
